# shm-broadcast-go

单机共享内存零拷贝广播通道：同一台机器上的**一个写入进程**向可被
**多个读取进程**映射的段文件追加事件，每个订阅者维护相互独立的
读取进度。纯 Go 标准库实现，无 CGO、无外部依赖。

## 特性

- **零拷贝**：事件直接写入共享内存，订阅者原地读取，无序列化、无 IPC 拷贝。
- **事件原子性**：单条事件完整且不可分割，读取方永远不会观察到写入中间状态。
- **订阅者隔离**：每个订阅者独立进度；任何订阅者落后都不影响其他订阅者，
  也不通过锁阻塞写入方。
- **两种积压策略**：写满后阻塞写入（`PolicyBlock`）或覆盖最旧事件
  （`PolicyOverwrite`）。
- **崩溃恢复**：进程崩溃后重新挂载同一段文件，已提交事件仍然可读，
  未提交写入不可见、不错位。
- **代际标识**：同一路径重建段后，旧代际的读取进度被明确判定为失效。
- **诊断接口**：可读取写入位置、各订阅者进度与积压量。

## 快速上手

```go
// 写入方（同一时刻只允许一个写入进程，由文件排他锁保证）
w, _ := broadcast.Create("/tmp/events.seg", broadcast.Options{
    Capacity: 16 << 20,                     // 数据区容量，按页对齐
    Policy:   broadcast.PolicyOverwrite,    // 或 PolicyBlock
})
seq, _ := w.Write([]byte("hello"))
w.Close()

// 订阅方（起点为段内当前保留的最旧事件）
sub, _ := broadcast.Subscribe("/tmp/events.seg")
ev, err := sub.Next()        // 无新事件时 err == broadcast.ErrEmpty
fmt.Println(ev.Seq, string(ev.Data))

// 崩溃恢复：写入进程退出后重新挂载，从最后提交位置继续
w2, _ := broadcast.OpenWriter("/tmp/events.seg")
```

### 断点恢复

```go
pos := sub.Position()                        // 保存进度（含代际）
sub2, err := broadcast.SubscribeAt(path, pos) // 同代际可恢复；
// 段已重建 → ErrGenerationMismatch；进度已被覆盖 → *LaggedError
```

### 处理数据缺口（PolicyOverwrite）

```go
ev, err := sub.Next()
var lagged *broadcast.LaggedError
if errors.As(err, &lagged) {
    // lagged.HeadSeq 是当前最旧可用事件序号，缺口大小可据此计算
    sub.Resync()          // 显式确认缺口，对齐到最旧可用事件
    // 或 sub.ResyncToLatest() 丢弃全部积压
}
```

## 一致性语义

### 提交协议

每条事件在数据区中的记录为：

```
+0  u64 提交字（原子）：高 32 位 = 事件序号低 32 位；低 32 位 = 填充标记 | 长度
+8  u64 CRC 字：载荷的 CRC32(Castagnoli)
+16 载荷（按 8 字节对齐填充）
```

写入方按以下顺序提交一条事件：

1. 以 8 字节原子存储写入载荷；
2. 原子写 CRC 字；
3. 原子写提交字（release）；
4. 原子推进头部 `tail`（release）——**tail 是读取方的可见性门槛**。

读取方只会读取 `tail` 之前的记录，并在读取前后校验提交字中的序号、
载荷 CRC 以及 `head` 水位。因此：

- 不会观察到正在写入的中间状态；
- 覆盖竞争下撕裂的载荷会被 CRC/序号校验识别，转化为 `*LaggedError`，
  而不会静默呈现为有效数据；
- 载荷读写均通过按字原子访问完成，`go test -race` 下无数据竞争。

### 可见性与顺序

- 事件按写入顺序提交，序号从 0 单调递增（仅统计正式事件）。
- 所有跨进程同步通过映射区上的原子操作完成（Go 内存模型中
  `sync/atomic` 的顺序一致性语义），同机多进程共享同一页缓存，
  无需额外系统调用。
- 写入方互斥由段文件上的 `flock(LOCK_EX|LOCK_NB)` 保证，
  进程死亡时内核自动释放。

### 零拷贝视图的有效期

`Event.Data` 直接引用共享内存：

- **PolicyBlock**：订阅者槽位发布的是*读取水位*（仍可能正在阅读的
  最旧事件起点），写入方不会覆盖任何订阅者水位及之后的字节。
  因此返回的视图在下一次 `Next`/`Wait`/`Resync` 调用前保证有效。
- **PolicyOverwrite**：写入方随时可能覆盖，视图只在返回时点上
  校验有效；需要保留请自行拷贝（如 `bytes.Clone`）。

### 崩溃恢复模型

- 已提交事件（`tail` 之前）在进程崩溃后仍然可读——它们驻留在
  操作系统页缓存中，不依赖写入进程存活。
- 未提交的写入（崩溃发生在推进 `tail` 之前）对任何读取方不可见。
- 重新挂载（`OpenWriter`）从头部记录的 `tail`/`committed` 精确恢复，
  残留的中间字节会被后续写入覆盖，不会造成重复或错位。
- 崩溃订阅者的残留槽位由写入方/新订阅者通过 PID 存活检测自动回收，
  不会永久阻塞 `PolicyBlock` 下的写入方。
- 注意：不保证操作系统级掉电（非进程崩溃）后的持久性，段文件
  不做 `msync`/`fsync`。

### 代际

- `Create` 在同一路径**原地重建**段（不 unlink，保持 inode），
  并分配新的随机 64 位代际标识写入头部。
- 已映射旧段的订阅者在校验时发现代际变化，后续读取返回
  `ErrGenerationMismatch`；旧代际的 `Position` 传给新段同样被拒绝，
  不会把旧偏移当作新段进度。
- 重建途中崩溃会留下魔数未就绪的段，挂载方收到 `ErrInvalidSegment`，
  重新 `Create` 即可恢复。

## 段文件对外约定

段文件是普通文件，按本机字节序解释，仅供同机进程映射：

```
[0,128)           固定头部（见下）
[128, hdrSize)    订阅者槽位数组，每槽 32 字节
[hdrSize, EOF)    数据区：环形字节缓冲，记录 8 字节对齐
```

固定头部字段（偏移/字节）：

| 偏移 | 字段        | 说明                                       |
|-----:|-------------|--------------------------------------------|
|  0   | magic       | `0x53484D2D42434E31`，最后写入，作为就绪标记 |
|  8   | version     | 格式版本，当前为 1                          |
| 16   | generation  | 代际标识（重建时变更）                       |
| 24   | headerSize  | 数据区起始偏移                              |
| 32   | capacity    | 数据区容量（页对齐）                         |
| 40   | policy      | 0=Block，1=Overwrite                        |
| 48   | maxSlots    | 订阅者槽位数                                |
| 56   | tail        | 已提交写入位置（单调字节偏移，可见性门槛）    |
| 64   | head        | 最旧可用记录偏移                             |
| 72   | headSeq     | head 处记录的事件序号                        |
| 80   | committed   | 已提交事件总数（下一个待分配序号）            |
| 88   | createdAt   | 创建时间（Unix 纳秒）                        |

订阅者槽位（32 字节）：`id`(0=空闲)、`offset`（读取水位）、
`seq`、`pid`。订阅者只写自己的槽位；`offset`/`seq` 先于 `id`
发布，供写入方背压与诊断读取。

数据区记录见「提交协议」。记录不能放入尾部剩余空间时，先提交一条
**填充记录**（填充标记位置位，长度为整段填充跨度），再从数据区
起点写下一条记录。

### 诊断

`Writer.Stats()` / `Subscriber.Stats()` 返回快照：代际、容量、
`head`/`tail`、已提交事件数、积压字节数，以及每个订阅者的
读取水位、落后字节数与落后事件数。

## 积压策略详述

| | PolicyBlock | PolicyOverwrite |
|---|---|---|
| 段满时 | 写入方阻塞（`TryWrite` 返回 `ErrWouldBlock`） | 覆盖最旧事件 |
| 慢订阅者 | 通过读取水位施加背压 | 收到 `*LaggedError`，可 `Resync` |
| 无订阅者 | 不阻塞（head 随写入推进） | 不阻塞 |
| 死订阅者 | 槽位被回收，不阻塞 | 无影响 |

注意：`PolicyBlock` 下，**存活且已注册**的慢订阅者会对写入方施加
背压（这是该策略的语义）；订阅者之间互不影响，读取路径不持有任何锁。

## 限制

- 仅支持类 Unix 系统（darwin/linux 等）；段文件按本机字节序解释。
- 单写入进程，多读取进程；读取方数量受 `MaxSubscribers` 限制（默认 64）。
- 单条事件载荷上限约 1GiB，且记录总长不得超过段容量。
- 段容量上限约 2GiB。

## 测试

```sh
go test ./...        # 全部测试
go test -race ./...  # 含竞态检测
```

覆盖：多订阅者进度隔离、两种积压策略、崩溃后重新挂载（含 SIGKILL
中写）、代际切换、高并发读写、多进程广播与死订阅者回收。
